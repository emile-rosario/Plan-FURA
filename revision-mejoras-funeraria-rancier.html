Backend — Seguridad
Crítico Sin Rate Limiting — Fuerza Bruta en /login y /register

Los endpoints /login y /register no tienen ningún límite de peticiones. Un atacante puede probar miles de contraseñas o crear miles de cuentas sin restricción.

Solución: Agregar slowapi (rate limiter para FastAPI):

# requirements.txt
slowapi==0.1.9

# main.py
from slowapi import Limiter, _rate_limit_exceeded_handler
from slowapi.util import get_remote_address
from slowapi.errors import RateLimitExceeded

limiter = Limiter(key_func=get_remote_address)
app.state.limiter = limiter
app.add_exception_handler(RateLimitExceeded, _rate_limit_exceeded_handler)

# auth.py — en el endpoint login:
@router.post("/login")
@limiter.limit("5/minute")
async def login(request: Request, ...):
Crítico Credencial admin hardcodeada en seed_data()

La contraseña Admin@2025 está visible en texto plano dentro del código fuente en main.py. Cualquiera con acceso al repositorio conoce la contraseña de producción.

Solución: Leerla desde variables de entorno:

# config.py — agregar:
ADMIN_EMAIL: str = "admin@funerariarancier.com"
ADMIN_PASSWORD: str = ""  # Obligatorio en .env

# main.py — seed_data():
admin = User(
    password=hash_password(settings.ADMIN_PASSWORD),
    # ...
)
Alto Sin Refresh Token — Solo Access Token (60 min)

El sistema solo emite access tokens de 60 minutos sin refresh token. El usuario queda deslogueado cada hora obligando a re-autenticarse, o si se alarga el tiempo se crea una ventana de ataque mayor.

Solución: Implementar par de tokens access (15 min) + refresh (7 días) almacenado en cookie HttpOnly:

def create_refresh_token(data: dict) -> str:
    return create_access_token(data, expires_delta=timedelta(days=7))

# En login — devolver refresh en cookie HttpOnly:
response.set_cookie(
    key="refresh_token", value=refresh_token,
    httponly=True, secure=True, samesite="lax",
    max_age=604800
)
Alto Token JWT almacenado en localStorage — Vulnerable a XSS

En api.js, el token se guarda con localStorage.setItem("fr_token", token). Cualquier script inyectado (XSS) puede leerlo y suplantar al usuario. Esta es una vulnerabilidad estándar documentada por OWASP.

Solución: Mover el access token a memoria JS (variable) y el refresh token a cookie HttpOnly que el servidor establece. El frontend nunca debería poder leer el refresh token.

Alto TrustedHostMiddleware importado pero nunca configurado

En main.py se importa TrustedHostMiddleware pero nunca se registra en la app. No tiene efecto alguno actualmente.

Solución:

app.add_middleware(
    TrustedHostMiddleware,
    allowed_hosts=["funerariarancier.com", "www.funerariarancier.com"]
)
Medio Endpoints /forgot-password y /reset-password no existen en backend

El archivo api.js llama a /forgot-password y /reset-password, y existen migraciones SQL para estas tablas, pero los routers nunca fueron implementados en Python. El frontend intentará llamar a rutas que devuelven 404.

Solución: Crear backend/app/routers/password_reset.py que implemente el flujo completo con email de recuperación (usando la dependencia email.py ya existente).

password_reset.py faltante email.py ya está listo migraciones SQL ya existen
Medio Verificación de email no implementada

Existe la migración add_email_verification.sql pero no hay lógica en los routers que envíe el email de verificación ni que bloquee usuarios no verificados. El registro acepta cualquier email sin validar que realmente le pertenece al usuario.

Solución: En register, enviar email con token único. Agregar campo email_verificado al modelo User y bloquearlo en el login hasta verificar.

Backend — Arquitectura y Calidad de Código
Alto Sin paginación en endpoints de listado

Los endpoints GET /ataudes, GET /planes y GET /contacto devuelven todos los registros sin límite. Con 1000+ ataúdes o mensajes, la respuesta será enorme y lenta.

Solución: Agregar parámetros skip y limit:

@router.get("", response_model=list[CoffinResponse])
def list_coffins(
    skip: int = Query(0, ge=0),
    limit: int = Query(20, ge=1, le=100),
    disponible: Optional[bool] = Query(None),
    db: Session = Depends(get_db),
):
    q = db.query(Coffin)
    if disponible is not None:
        q = q.filter(Coffin.disponible == disponible)
    total = q.count()
    items = q.order_by(Coffin.precio).offset(skip).limit(limit).all()
    return {"total": total, "items": items, "skip": skip, "limit": limit}
Alto Campo beneficios almacenado como Text/JSON string en lugar de JSONB

El campo beneficios en el modelo Plan es Column(Text) que guarda un string JSON (json.dumps([...])). PostgreSQL tiene tipo nativo JSONB que permite índices, queries y validación automática.

Solución:

from sqlalchemy.dialects.postgresql import JSONB

class Plan(Base):
    # ...
    beneficios = Column(JSONB, default=list)  # ✅ tipo nativo, sin json.dumps

También eliminar los json.dumps() en seed_data().

Alto Sin tests unitarios ni de integración

El requirements.txt incluye pytest e httpx (cliente de testing para FastAPI), pero no existe ningún archivo de pruebas en el proyecto. Cambios en producción se hacen sin red de seguridad.

Solución: Crear backend/tests/ con al menos:

test_auth.py — register/login/token test_planes.py — CRUD admin test_suscripciones.py — contratar/cancelar conftest.py — base de datos de test
Medio Rol de usuario como string sin validación — debería ser Enum

En el modelo User, el campo rol es Column(String(20)). Nada impide que se guarde "superadmin", "moderator" u otro valor inválido. La lógica de autorización se basa en comparar strings.

Solución:

class RolUsuario(str, enum.Enum):
    cliente = "cliente"
    admin = "admin"

class User(Base):
    rol = Column(SAEnum(RolUsuario, name="rol_usuario"), default=RolUsuario.cliente)
Medio Formulario de contacto sin validación de spam ni anti-flood

El endpoint POST /contacto es completamente público y sin ningún límite. Un bot puede enviar miles de mensajes, inundando la base de datos y el correo del administrador.

Solución: Aplicar rate limiting (3/hour por IP) y agregar un honeypot field oculto en el formulario frontend. Opcionalmente, integrar reCAPTCHA v3 invisible.

Medio Sin logs de auditoría para acciones admin

Las operaciones destructivas (eliminar plan, eliminar ataúd) solo tienen un logger.info() que va a stdout. No hay tabla de auditoría persistente que registre quién hizo qué y cuándo.

Solución: Crear modelo AuditLog en la base de datos con campos: user_id, accion, entidad, entidad_id, timestamp. Registrar todas las operaciones admin.

Bajo Delete físico en lugar de soft delete

Los endpoints DELETE /planes/{id} y DELETE /ataudes/{id} eliminan el registro permanentemente. Esto puede romper referencias históricas (ej: una suscripción que referencia un plan eliminado).

Solución: Ya tienes el campo activo en Plan y disponible en Coffin. Cambiar delete a soft delete: plan.activo = False en lugar de db.delete(plan). Agregar la FK con ondelete="RESTRICT" ya previene algunos casos.

Bajo Archivos subidos sin validación real de contenido (magic bytes)

En uploads.py, la validación se basa solo en file.content_type, que es un header enviado por el cliente y puede ser falsificado. Se puede subir un ejecutable renombrándolo a .jpg.

Solución: Validar los "magic bytes" reales del archivo:

import imghdr

detected = imghdr.what(None, h=contents[:32])
if detected not in ["jpeg", "png", "webp"]:
    raise HTTPException(415, "El contenido no es una imagen válida.")

Frontend — Rendimiento y Configuración
Crítico API_URL hardcodeada a localhost — No funcionará en producción

En api.js, la URL del backend es const API_URL = "http://127.0.0.1:8000". Cuando el sitio se despliegue en producción, todas las llamadas API fallarán porque apuntarán a la máquina local del desarrollador.

Solución: Usar una variable de entorno o detectar el entorno automáticamente:

const API_URL = window.location.hostname === "localhost"
    ? "http://127.0.0.1:8000"
    : "https://api.funerariarancier.com";

// O mejor: un archivo de configuración separado por entorno
// config.js → window.APP_CONFIG = { apiUrl: "..." }
Alto Tailwind CSS cargado desde CDN — Sin purge, bundle ~3.5 MB

Todas las páginas cargan <script src="https://cdn.tailwindcss.com">. Esto incluye las ~3.5 MB completas de Tailwind sin ningún purge. En producción, debería compilarse solo con las clases usadas (típicamente 5-15 KB).

Solución A (simple): Instalar Tailwind CLI y compilar un CSS optimizado.

Solución B (mínima): Si quieres mantener CDN para el prototipo, al menos agrega:

<script>tailwind.config = { /* config aquí */ }</script>
<link rel="preload" as="style" href="https://cdn.tailwindcss.com"/>
Alto CSS duplicado en cada página HTML — Sin stylesheet compartido

Cada página (index.html, login.html, dashboard.html, etc.) tiene su propio bloque <style> repitiendo las mismas reglas: .btn-primary, .nav-link, .blue-line, variables CSS, etc. Cambiar el color primario requiere editar 7 archivos.

Solución: Crear frontend/assets/css/main.css con todos los estilos compartidos y referenciarlos en cada página. Mantener solo los estilos únicos de cada página inline.

Medio Fuentes de Google cargadas sin font-display: swap

Las fuentes se cargan con <link href="https://fonts.googleapis.com/css2?..."> pero sin especificar &display=swap. Esto puede causar FOIT (Flash of Invisible Text) donde el texto es invisible mientras la fuente carga.

Solución:

<link href="https://fonts.googleapis.com/css2?family=Playfair+Display:ital,wght@0,400;0,700&family=DM+Sans:wght@400;600&display=swap" rel="stylesheet"/>
Medio Sin favicon ni meta OG — Pobre SEO y compartibilidad

El sitio no tiene favicon (se muestra el icono genérico del browser), ni metaetiquetas Open Graph para cuando se comparte en redes sociales. Solo index.html tiene <meta name="description">; las otras páginas no.

Agregar a todas las páginas:

<link rel="icon" href="assets/img/favicon.ico"/>
<meta property="og:title" content="Funerarias Rancier"/>
<meta property="og:description" content="Servicio digno y humano."/>
<meta property="og:image" content="assets/img/og-image.jpg"/>
<meta name="description" content="..."/>

Frontend — UI/UX y Accesibilidad
Alto Dashboard no es responsive en mobile — Sidebar fija de 264px

El dashboard.html tiene un sidebar con clase w-64 (256px) que nunca se oculta en pantallas pequeñas. En un teléfono de 375px solo quedan ~119px para el contenido principal, haciendo la interfaz inutilizable.

Solución: Convertir el sidebar en un drawer deslizable en mobile usando clases responsive de Tailwind:

<aside id="sidebar"
  class="fixed inset-y-0 left-0 z-40 w-64 -translate-x-full
          lg:relative lg:translate-x-0 transition-transform duration-300">
  <!-- contenido sidebar -->
</aside>
<div id="overlay" class="fixed inset-0 bg-black/40 z-30 hidden lg:hidden"></div>
Alto Animaciones sin respeto a prefers-reduced-motion

Las animaciones fadeUp y transiciones en cards se aplican a todos los usuarios. Personas con epilepsia fotosensible o mareos vestibulares necesitan que las animaciones se desactiven cuando tienen activada la opción de sistema "reducir movimiento".

Agregar al CSS global:

@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
  }
}
Alto Sin skeleton screens ni estados de carga en el dashboard

El dashboard carga los datos del usuario, el plan activo y las estadísticas de forma asíncrona. Durante la carga, los espacios están vacíos o muestran "—" y "Cargando...". Esto crea un efecto de Layout Shift (CLS alto) y una experiencia visual inestable.

Solución: Agregar skeleton placeholders mientras se esperan los datos:

<div class="animate-pulse space-y-3">
  <div class="h-4 bg-gray-200 rounded w-3/4"></div>
  <div class="h-4 bg-gray-200 rounded w-1/2"></div>
</div>
Medio Formulario de login sin label visible en inputs

Los campos de email y contraseña en login.html usan solo placeholder como guía. Cuando el usuario empieza a escribir, el placeholder desaparece y no hay label visible que indique qué campo es. Esto viola WCAG 2.1 criterio 1.3.5 y dificulta el uso para personas con discapacidades cognitivas.

Solución: Siempre acompañar el placeholder con un <label> explícito, aunque sea con un diseño "flotante" (floating label pattern).

Medio Navegación del dashboard usa onclick inline en HTML

Los elementos del sidebar usan onclick="showSection('overview')" directamente en el HTML. Esto mezcla estructura y comportamiento, dificulta el mantenimiento y el testing, y puede fallar en entornos con Content Security Policy estricto.

Solución: Usar data-* atributos y event listeners en JS:

<div class="sidebar-link" data-section="overview">Resumen</div>

// En el JS:
document.querySelectorAll('[data-section]').forEach(el => {
    el.addEventListener('click', () => showSection(el.dataset.section));
});
Medio Sin página 404 personalizada

El sitio no tiene una página 404.html. Cuando un usuario escribe una URL incorrecta o un enlace está roto, verá el error genérico del servidor en lugar de una página de la marca con navegación de vuelta al inicio.

Solución: Crear frontend/404.html con el diseño de la marca, un mensaje amigable y un botón "Volver al inicio".

Medio Botón WhatsApp flotante sin aria-label ni texto de ayuda

El botón flotante de WhatsApp en index.html es solo un ícono SVG dentro de un <a>. Sin texto alternativo, los lectores de pantalla lo anuncian como "link" sin indicar para qué sirve.

Solución:

<a href="https://wa.me/..."
   class="whatsapp-float"
   aria-label="Contactar por WhatsApp"
   title="Contáctanos por WhatsApp"
   target="_blank"
   rel="noopener noreferrer">
  <!-- SVG aquí -->
</a>
Medio Sin confirmación visual al cancelar suscripción — acción destructiva sin diálogo

El botón "Cancelar Plan" en el dashboard ejecuta la cancelación directamente. Cancelar un plan funerario activo es una acción seria e irreversible que debería tener un diálogo de confirmación explícito.

Solución: Mostrar un modal de confirmación con texto claro sobre las consecuencias antes de proceder. El botón destructivo debe estar en rojo y separado del botón de cancelar el diálogo.

Bajo El catálogo no tiene estado vacío cuando no hay ataúdes disponibles

Si la API devuelve una lista vacía de ataúdes, el grid simplemente queda en blanco sin ningún mensaje al usuario explicando por qué no hay contenido.

Solución: Mostrar un empty state con icono, texto explicativo y un call-to-action (ej: "Contáctanos para consultar disponibilidad").

Bajo Sin indicador de "scroll para más" en la landing page de hero

La sección hero de index.html ocupa toda la pantalla. No hay ninguna indicación visual de que hay más contenido debajo. Muchos usuarios, especialmente en mobile, pueden no darse cuenta de que hay servicios, planes y testimonios debajo del fold.

Solución: Agregar un indicador de scroll animado (flecha o punto pulsante) al fondo de la sección hero que desaparezca al hacer scroll.
